# Release Pipeline Design — Single Signed Manifest + Lifecycle Tiers

Status: **Adopted** (maintainer decision, 2026-07-12).

This document specifies ClotoCore's distribution pipeline: a single signed
release manifest that every update consumer reads, with release channels
mapped 1:1 to the tiers of the [Release Lifecycle
Standard](https://github.com/Cloto-dev/cpersona/blob/master/docs/RELEASE_LIFECYCLE_STANDARD.md)
(v1.3, piloted in cpersona). ClotoCore adopts that standard as the second
pilot repository: cpersona is the reference for policy operation, ClotoCore
is the reference for **enforcing the policy in distribution infrastructure**.

## 1. Motivation

The pipeline before this design had three independent version-resolution
mechanisms, none of which could express pre-release channels:

1. **Tauri updater** — reads `latest.json` from
   `releases/latest/download/`, which GitHub hard-wires to the newest
   non-prerelease release. Pre-release update channels were explicitly
   deferred (`dashboard/src/lib/tauri.ts`).
2. **install.sh** — resolves "latest" through the unauthenticated GitHub
   API (60 req/h rate limit; brittle in CI and corporate networks) with
   hand-rolled platform detection.
3. **Dashboard update check** — a no-op outside the desktop app.

A PyPI-based channel was considered and rejected: uvx conventions belong to
the MCP *server* layer (cf. `cembedding` on PyPI), not to the host
application, and every stability property PyPI would have provided is
achievable channel-agnostically with an owned manifest. A stable, predictable
pipeline — not presence on a particular index — is what platform adopters
need.

**Design principle: one logical channel.** Version resolution has exactly
one source of truth (the signed manifest); storage hosts behind it are
interchangeable mirrors. Today the only storage is GitHub Releases.

## 2. Goals / non-goals

Goals:

- Adopt the Release Lifecycle Standard's tier vocabulary and rules, enforced
  structurally by the manifest's channel-resolution logic.
- Pre-release (`-alpha.N` / `-beta.N` / `-rc.N`) distribution on an opt-in
  channel, for both the desktop app and the headless kernel.
- Experimental-build warnings at every consumer surface.
- Remove the unauthenticated GitHub API from the install path.

Non-goals:

- **PyPI distribution.** Only defensive name registration of `clotocore` /
  `cloto` (placeholder packages, maintainer-held credentials).
- **Shell/core split** (spawning the kernel as a child process of a thin
  Tauri shell). Deliberately deferred; this design neither requires nor
  precludes it.
- Changing artifact build jobs. The existing build matrix, minisign
  signatures, SHA256SUMS + cosign bundle, and the two-phase upload fix all
  stay as-is.

## 3. Tiers and channels

Channels are named after the standard's tiers, verbatim:

| Channel | Tier (standard §1) | Resolves to |
| --- | --- | --- |
| `stable` (default) | Stable | Newest release of the certified stable line |
| `current` | Current | Newest final (non-pre-release) release |
| `experimental` | Experimental | Newest release including pre-releases |

Resolution is inclusive downward: `current` ⊇ `stable`, `experimental` ⊇
`current`. A user following `experimental` moves to the final release when
it ships; a user following `current` moves to it immediately, a `stable`
user only after certification.

This makes two standard rules structural instead of conventional:

- **Installer opt-in property (§2.1)** — the default channel is `stable`;
  no default-configured consumer can ever resolve a pre-release.
- **Default distribution serves Stable (§4)** — the channel default *is*
  the pin.

Alpha vs beta is expressed in the version string only; there is a single
`experimental` channel (matching React's release-channel model referenced by
the standard). Versions use semver as already tagged (`v0.6.8-beta.1`); no
version-scheme translation exists anywhere in the pipeline.

### 3.1 Initial state: no certified stable line yet

ClotoCore has never certified a line as Stable (the 0.6.8 soak, an earlier decision, will be the first certification event). The standard does not define
this state — reported upstream as a standard defect for v1.1 (§9 below).

Rule: **while `stable_line` is null, the `stable` channel aliases
`current`**, and the generated stable view carries `"stable_alias": true` so
consumers can surface "Stable line not yet certified" in UI.

## 4. The manifest

### 4.1 Master manifest (`manifest.json`)

Generated by CI as a pure function of (GitHub Releases state, lifecycle
file). Illustrative schema:

```json
{
  "schema_version": 1,
  "generated_at": "2026-07-12T00:00:00Z",
  "lifecycle": {
    "stable_line": null,
    "certified_at": null
  },
  "releases": [
    {
      "version": "0.6.8-beta.1",
      "tier": "experimental",
      "pub_date": "2026-06-13T00:00:00Z",
      "notes_url": "https://github.com/Cloto-dev/ClotoCore/releases/tag/v0.6.8-beta.1",
      "desktop": {
        "windows-x86_64": { "url": "…", "sha256": "…", "signature": "…" },
        "darwin-aarch64":  { "url": "…", "sha256": "…", "signature": "…" }
      },
      "kernel": {
        "linux-x64":   { "url": "…", "sha256": "…" },
        "macos-arm64": { "url": "…", "sha256": "…" }
      }
    }
  ],
  "advisories": [
    {
      "bug_id": "bug-386",
      "severity": "critical",
      "affected": ">=0.6.0 <0.6.7",
      "fixed_in": "0.6.7",
      "symptom_check": "legacy_data_dir_drift",
      "summary": "…"
    }
  ]
}
```

- `tier` is derived, never hand-written: a semver pre-release suffix ⇒
  `experimental`; otherwise `stable` if the release's `X.Y` line equals
  `lifecycle.stable_line`, else `current`.
- `desktop` platform keys match the Tauri updater's existing vocabulary
  (`windows-x86_64`, `linux-x86_64`, `darwin-aarch64`, `darwin-x86_64`);
  `kernel` keys match the CLI archive naming (`linux-x64`, `linux-arm64`,
  `macos-x64`, `macos-arm64`, `windows-x64`).
- `signature` is the existing per-artifact minisign signature (unchanged);
  `sha256` comes from the release's `SHA256SUMS.txt`.
- `advisories` (additive, DEFENDER_DESIGN.md §5) is extracted from
  `qa/issue-registry.json` entries that carry an opt-in `advisory` object
  (`{ "affected": "<semver range>", "symptom_check": "<check name>" }`).
  Consumed by `clotocore doctor` and the kernel health scan;
  recommendation-only on the client (the defender never auto-updates).

### 4.2 Lifecycle file (`.release/lifecycle.json`)

```json
{ "stable_line": null, "certified_at": null }
```

Lives in the repository. **Certification (standard §2.3) = a reviewed PR
that sets `stable_line`** — an explicit, auditable maintainer event, exactly
matching "the pin flips on certification, not on release" (§4). The same PR
updates `SUPPORT.md`'s status table.

### 4.3 Channel views

From the master manifest, CI generates one Tauri-updater-format `latest.json`
per channel — `stable.json`, `current.json`, `experimental.json` — each
containing the resolved newest version for that channel with its `platforms`
map. These are plain static files; the Tauri updater consumes them without
modification.

### 4.4 Storage: rolling feed release

All feed files are assets of a single rolling GitHub release with the fixed
tag **`updater-feed`** (marked prerelease so it never captures the GitHub
"Latest" badge):

```
https://github.com/Cloto-dev/ClotoCore/releases/download/updater-feed/manifest.json
https://github.com/Cloto-dev/ClotoCore/releases/download/updater-feed/manifest.json.minisig
https://github.com/Cloto-dev/ClotoCore/releases/download/updater-feed/stable.json
https://github.com/Cloto-dev/ClotoCore/releases/download/updater-feed/current.json
https://github.com/Cloto-dev/ClotoCore/releases/download/updater-feed/experimental.json
```

These are direct CDN URLs — no API calls, no rate limits. Alternatives
considered: GitHub Pages (rejected: couples releasing to the site deploy
pipeline, a second publish surface) and per-release assets only (rejected:
no stable URL for channel resolution).

**Ordering preserves the two-phase upload fix**: the feed is regenerated
*after* the versioned release's binaries are fully uploaded, so a client
never sees a version whose artifacts are still uploading. The feed update
replaces the current "append latest.json last" phase as the commit point of
a release.

### 4.5 Signing

`manifest.json.minisig` is a minisign signature by the **same key already
embedded in every client** as the Tauri updater `pubkey`
(`tauri.conf.json`), signed in CI with the existing secret. Consumers that
can verify minisign (kernel, future self-updater) verify the manifest
signature; `install.sh` verifies per-artifact `sha256` from the manifest
(and the minisign signature when a `minisign` binary is available). The
per-artifact Tauri signatures and the cosign-signed `SHA256SUMS.txt` bundle
are unchanged.

#### Key management (runbook)

The signing key pair (key id `66FD7C51 72819DEC`, generated 2026-07-12)
lives in three places that MUST stay in sync:

1. `~/.tauri/cloto-signing-key.key` (+ `.password`) on the maintainer's
   machine — **back both up in the password manager**; the file system copy
   is not a backup.
2. Repository secrets `TAURI_SIGNING_PRIVATE_KEY` /
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (what CI signs with).
3. The `pubkey` in `dashboard/src-tauri/tauri.conf.json` (what every
   shipped client verifies against).

**Rotation procedure**: regenerate with `tauri signer generate`, then update
(2) and (3) **in the same change**, then run the Update Feed workflow and
confirm the published `manifest.json.minisig` key id matches the new
pubkey. History lesson (2026-07-12): the 2026-03-08 rotation updated (3)
but not (2), which silently broke desktop auto-update signature
verification for every release from v0.6.0 to v0.6.8-beta.1 — the mismatch
was only caught when the feed's manifest signature was machine-verified
against the client-embedded pubkey. Clients on those versions must
reinstall manually once; auto-update verifies from the first release signed
with the current key.

## 5. Consumers

### 5.1 Tauri updater (desktop)

- A new **update channel** setting (default `stable`), persisted alongside
  the existing auto-update preference.
- The Rust side builds the updater with the endpoint
  `…/updater-feed/{channel}.json` at check time (Tauri v2 supports runtime
  endpoint configuration); the static endpoint in `tauri.conf.json` remains
  `…/updater-feed/stable.json` as the default.
- Switching **to** `experimental` requires an explicit confirmation dialog
  quoting the standard: *"Experimental releases are opt-in only, with no
  guarantees. Fixes ship in the next pre-release."*
- Channel downgrade note: switching from `experimental` back to `stable`
  does not downgrade the installed version; the app stays put until the
  stable channel surpasses it (correct semver behavior, surfaced as a hint
  in the settings UI).

### 5.2 install.sh (headless kernel)

Resolves through the manifest instead of the GitHub API:
`CLOTO_CHANNEL` (default `stable`) selects the channel, `CLOTO_VERSION`
still pins an exact version. Platform selection uses the manifest's `kernel`
keys; downloads are sha256-verified against the manifest. The
unauthenticated `api.github.com` call is removed.

### 5.3 Dashboard update check (browser / headless mode)

Currently a no-op outside Tauri. With the feed, browser mode can read
`manifest.json` and report position ("you are on Current; Stable is
v0.6.7") without any GitHub API dependency. Display-only in this design; a
kernel self-update flow is future work and must gate on manifest signature
verification (§4.5).

### 5.4 Legacy endpoint

`releases/latest/download/latest.json` keeps being published on final
releases so already-installed apps continue to update; their first update
onto a feed-aware build migrates them to the channel endpoints. The legacy
endpoint's semantics equal the `current` channel (GitHub "latest" knows
nothing of certification) — acceptable for the transition, identical to
pre-design behavior.

## 6. Experimental warnings

Experimental is detectable **locally** — a semver pre-release suffix on the
running version — with no network dependency. Four surfaces:

1. **Dashboard badge** (always visible while running a pre-release):
   "Experimental build — opt-in, no guarantees".
2. **Channel-switch confirmation dialog** (§5.1).
3. **install.sh** — a warning block when `CLOTO_CHANNEL=experimental`
   or when `CLOTO_VERSION` pins a pre-release.
4. **Kernel boot log** — one `WARN` line on pre-release builds.

Tier *labels* beyond experimental (Current vs Stable) are not locally
derivable — they require the certification record — so the badge mechanism
only ever asserts "experimental", and channel-position info comes from the
manifest (§5.3).

## 7. Standard adoption artifacts (checklist §5)

- `SUPPORT.md` — tier table, lifecycle summary, status table. Initial
  status: 0.6.x = Current (no Stable line; 0.6.8-beta.1 = Experimental).
- `SECURITY.md` — revised to reference `SUPPORT.md` for supported versions.
- README section pointing at both.
- **Release gate (§2.2)**: cargo test + clippy (`-D warnings`) + fmt check +
  `verify-issues.sh` + CI green on the release PR.
- **Soak environment (§2.3)**: the maintainer's production desktop
  deployment.
- Adoption registry row in the standard's §7 (cpersona repo), noting the
  pilot-extension role.

## 8. Rollout phases

| Phase | Scope | CSC task |
| --- | --- | --- |
| P1 | This design doc; `SUPPORT.md` / `SECURITY.md` / README; adoption registry | T1, T5, T6 |
| P2 | `.release/lifecycle.json`; manifest + channel-view generation in `release.yml`; `updater-feed` rolling release; feed-regeneration `workflow_dispatch` (for certification flips) | T2 |
| P3 | Channel setting + runtime updater endpoint; experimental warnings (badge, dialog, boot WARN) | T3, T4 |
| P4 | `install.sh` manifest resolution | T7 |
| P5 | PyPI defensive registration (maintainer credentials) | T8 |

Each phase is independently shippable; P2 changes nothing for existing
clients (additive feed), P3 is where clients start reading it.

## 9. Feedback to the standard (v1.1 candidates)

   certified Stable line (§3.1's aliasing rule is the proposed text).
2. **Distribution mapping**: add a "manifest/feed" row to §4 alongside

   structurally rather than by registry convention.
